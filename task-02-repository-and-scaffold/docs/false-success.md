# False success: what was tested and what happened

Recorded at (UTC): 2026-11-01T13:41:00Z

This document describes the observed browser and database checks for the Task 2 fictional enquiry feature. It does not claim that HTTP 201 alone proves storage, and it does not claim that the feature is production-ready.

## What “false success” means here

A false success would be one of these:

- the browser shows a success message even though no row was saved;
- the application treats an HTTP 201 response as proof without checking the database;
- a read-only or failed database write is reported as a successful enquiry.

The implementation avoids the first two by showing success only after `response.status === 201` and an integer `id` in the response. The server sends that response only after its INSERT statement completes. The form is reset only on the success path. The third case was exercised with a real read-only database.

## Read-only failure exercise

The initialised database was opened read-only by starting a separate owned server with `DB_READONLY=1` (PID 4452, port 49610). No existing unrelated process was stopped.

Observed sequence:

1. `GET /` returned HTTP 200 and the form loaded. The verifier waited for `#enquiry-form` and filled the real fields.
2. The browser submitted valid fictional data: name `Fictional Browser Rejected`, phone `00000000000`, business type `other`.
3. The server attempted the INSERT. SQLite rejected it with `SQLITE_READONLY` and the message `attempt to write a readonly database`.
4. The server returned HTTP 500 with the generic message `Unable to save this demonstration enquiry. Your details remain below.`
5. The browser showed that error text. It did not show success. The name, phone and business-type values were still present in the form.
6. The row count before and after the failure was 2, and the exact rows were unchanged. A separate direct valid POST also returned HTTP 500 and added no row.
7. The read-only server was stopped, a writable server was started, the form was submitted again, and id 3 was saved with HTTP 201.

The actual server output is in [19-browser-write-failed-logs.txt](../evidence/19-browser-write-failed-logs.txt). It includes the `SQLITE_READONLY` error and the `"status":500` request log. The successful run and restoration are in [18-browser-write-succeeded-logs.txt](../evidence/18-browser-write-succeeded-logs.txt). The full sequence is in [21-browser-checks.txt](../evidence/21-browser-checks.txt).

## Why the browser did not show success on failure

The browser code follows this order:

1. POST the JSON values.
2. Parse the response.
3. Require HTTP 201 and an integer `id`.
4. Only then show the saved message and reset the form.

A 500 response, a non-201 response, a response without an integer id, a network error, or a response that cannot be parsed all take the error or uncertain path. The form is not reset on those paths, so the values remain for correction or retry. The server inserts with parameters before it sends 201, so the success message is not produced by the read path alone.

A lost response can still leave the outcome unknown. This demonstration has no idempotency key. The UI says so, and the README says to check stored rows before retrying. This document does not claim exactly-once submission.

## Limitations

- The checks ran against a local loopback server on one Windows machine with fictional data. They are not a security, accessibility or production reliability audit.
- The controlled failure was a read-only database. Disk-full, crash, lock timeout and partial-network failures were not simulated.
- The screenshots show a local rendering of a direct database query. They are evidence of persisted rows, not proof that a customer saw the same view.
- The feature is deliberately unauthenticated and has no real callback, payment, session or support workflow.
- The older evidence files `11-write-succeeded-logs.txt`, `12-database-rows.png` and `13-write-failed-logs.txt` were preserved. The run above is a later, browser-driven verification and is recorded separately as `18`–`26`.
